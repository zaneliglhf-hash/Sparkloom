# AI 灵感研究工作流设计

## 1. 项目目标

本项目是一个以 Codex 为入口的个人 AI 灵感研究工作台。用户可以自然地说出关于 AI 使用方式、AI 工作流或 AI 产品的想法；系统识别新灵感后，为它创建独立聊天，搜索场景相似的现有项目，并把研究结果保存为可长期积累和检索的 Markdown 报告。

第一阶段采用“项目级工作流 + Markdown 灵感库”，不开发独立图形界面。等积累约 10–20 个真实灵感后，再根据实际使用中反复出现的需求决定是否开发独立应用。

## 2. 使用范围

第一版只服务单个用户，主要研究：

- 个人在工作、学习、创作、研究和生活中使用 AI 的方法；
- Prompt、Skill、Agent、MCP 和自动化工作流；
- 可以直接使用或组合的 AI 工具；
- 从个人工作流自然延伸出的 AI 产品机会。

默认不研究模型训练、底层算法或纯学术问题，除非相关技术直接影响灵感的可行性。

## 3. 核心原则

1. 用户自然表达，不要求固定前缀、表单或模式标签。
2. 匹配以目标用户、问题和使用场景为主，不以技术栈或关键词相同代替场景相似。
3. 明显为个人自用的灵感优先考虑方便性、步骤减少、维护成本、隐私和稳定性，不强制进行商业价值分析。
4. 明显面向其他用户或具有产品化意图的灵感，才增加市场、竞争、差异化和付费可能性分析。
5. 结论必须与证据强度匹配。没有足够相似项目也是有效结论，不用低相关结果凑数。

## 4. 新灵感识别与聊天管理

当前聊天作为项目入口和导航中心。

### 4.1 识别规则

- 当用户明显提出一个新的 AI 使用想法、工作流构想或产品构想时，系统将其识别为新灵感。
- 当内容可能只是对已有灵感的补充、修改或普通讨论时，系统询问一次：“要把这个作为新灵感放到独立聊天研究吗？”
- 普通补充、讨论和对既有结论的修改留在原聊天中。

### 4.2 创建规则

识别为新灵感后，系统立即在 `Inspiration` 项目中创建独立聊天：

1. 使用简短、可辨认的中文标题；
2. 将用户的原始表述完整带入新聊天；
3. 同时带入固定研究目标和报告要求；
4. 后续澄清、检索、分析和报告生成均在新聊天中完成；
5. 入口聊天只保留创建结果与导航信息，避免不同灵感的上下文混杂。

若聊天创建失败，系统应在当前聊天继续研究并明确告知用户，不能丢失原始灵感。

### 4.3 重复灵感

当新内容与已有灵感高度重复时，系统先询问用户是继续原聊天，还是将其作为独立变体创建新聊天。

## 5. 单个灵感的研究流程

### 5.1 理解灵感

系统首先从自然语言中提取：

- 目标用户；
- 使用场景；
- 核心问题；
- 期望结果；
- 主要操作流程；
- 可能的形态，如工作流、Prompt、Skill、Agent、MCP、自动化或独立产品；
- 仅在有助于搜索时使用的技术特征。

若关键信息不足，系统每次只追问一个会实质影响检索方向的问题。

### 5.2 标准研究

每个灵感默认进行一次标准研究：

1. 在 GitHub 搜索开源实现、README、Topics、维护状态、许可证和近期活动；
2. 搜索官方产品网站、文档与定价信息，识别已上线的商业方案；
3. 搜索技术社区和用户社区，收集真实使用反馈与未解决问题；
4. 需要时扩展到论文、应用商店或相关垂直社区；
5. 汇总约 10–20 个合理候选；
6. 从中选出 3–5 个场景高度相似的项目重点分析。

所有易变化的信息均记录检索日期。链接失效或信息无法验证时明确标注，不将其作为强结论依据。

### 5.3 相似度判断

项目优先按照以下因素判断：

1. 解决的问题是否相同；
2. 面向的用户是否相近；
3. 用户工作流程是否相似；
4. 最终产出是否相同；
5. 技术实现是否有可借鉴之处。

前四项决定场景相似度；技术栈相同本身不能构成高度相似。GitHub Stars 只作为成熟度和关注度信号，不能直接代表产品价值。

## 6. 分析方式

### 6.1 所有灵感的共同分析

- 已有哪些相似方案；
- 现有方案覆盖了哪些需求；
- 它们遗漏、处理不佳或使用困难的部分；
- 至少一个由证据支持的差异化方向；
- 可以直接使用、组合或复用什么；
- 最低成本的下一步验证方式。

### 6.2 个人自用灵感

重点考虑：

- 是否更方便；
- 能减少多少步骤或重复操作；
- 是否能提高结果质量；
- 开发和长期维护成本；
- 能否通过现有工具快速拼装；
- 数据隐私、稳定性与模型依赖。

不强制分析市场规模、商业模式或他人付费意愿。

### 6.3 面向他人的产品灵感

在共同分析基础上增加：

- 目标用户的需求强度；
- 竞争拥挤程度；
- 用户价值与可替代方案；
- 产品差异化空间；
- 获客与付费可能性；
- 主要商业和合规风险。

系统根据灵感内容自动决定分析重点，不要求用户选择模式，也不在报告中加入没有实际意义的固定章节。

## 7. 报告结构

每个灵感生成一份独立 Markdown 报告。报告根据灵感类型裁剪，但通常包含：

1. 原始灵感、日期和研究状态；
2. 灵感解读，包括场景、问题、结果和可能形态；
3. 结论摘要，包括相似方案、差异化空间、重点项目和下一步；
4. 约 10–20 个候选项目的清单；
5. 3–5 个高度相似项目的重点对比；
6. 至少一个有证据支持的差异化方向；
7. 与灵感性质匹配的方便性、实用性或产品价值分析；
8. 一个成本尽可能低的验证实验；
9. 关键来源、检索日期与搜索范围。

最低成功标准是找到 3–5 个高度相似项目，并提出至少一个可信的差异化方向。如果客观上没有足够相似项目，报告必须说明搜索范围与未达到数量的原因，此时“缺少高度相似方案”替代数量目标。

## 8. 文件结构与归档

项目采用以下结构：

```text
Inspiration/
├─ AGENTS.md
├─ README.md
├─ ideas/
│  ├─ INDEX.md
│  └─ YYYY-MM-DD-idea-slug.md
├─ templates/
│  └─ idea-report.md
└─ docs/
   └─ superpowers/
      └─ specs/
         └─ 2026-08-13-ai-inspiration-workflow-design.md
```

职责如下：

- `AGENTS.md`：规定新灵感识别、聊天创建、研究与归档行为；
- `README.md`：说明项目用途和自然语言使用方式；
- `ideas/INDEX.md`：提供灵感总目录；
- `ideas/*.md`：保存每个灵感的独立研究报告；
- `templates/idea-report.md`：提供可裁剪的报告模板；
- `docs/superpowers/specs/`：保存项目设计文档。

报告文件名使用日期和稳定的英文短名；发生同名冲突时追加简短编号，不覆盖旧文件。

`ideas/INDEX.md` 至少记录：

- 灵感名称；
- 提出日期；
- 一句话描述；
- 状态：待研究、研究中、已完成或暂停；
- 报告链接。

## 9. 状态与数据流

单个灵感的状态流为：

```text
识别新灵感
  -> 创建独立聊天
  -> 建立待研究记录
  -> 澄清关键场景
  -> 搜索并筛选候选
  -> 完成重点对比和差异化分析
  -> 写入报告
  -> 更新总目录为已完成
```

中途停止时状态设为“暂停”，已有来源和阶段性结论仍写入报告，便于以后恢复。

## 10. 错误与降级处理

- 聊天创建失败：留在当前聊天继续研究，并说明失败，不丢弃灵感。
- 搜索渠道不可用：使用其他可用渠道，并在报告中记录缺失范围。
- 候选不足：不凑数，说明已检索渠道、关键词与判断依据。
- 信息冲突：优先官方和项目原始资料，同时记录无法消除的分歧。
- 项目失活：保留其作为思路证据，但显著标注维护状态。
- 文件名冲突：追加编号并保留现有文件。
- 写入中断：保留现有草稿，将索引状态设为研究中或暂停。

## 11. 验证方案

第一阶段完成后，用一个真实 AI 灵感进行端到端演练：

1. 自然表达灵感，不使用固定前缀；
2. 验证系统正确判断是否需要新聊天；
3. 验证独立聊天收到完整原始描述和研究任务；
4. 验证检索约 10–20 个候选，并正确选出高相似项目；
5. 验证重点结论有来源支持，链接可访问；
6. 验证报告写入正确位置且不覆盖旧文件；
7. 验证总目录状态和链接正确；
8. 验证个人自用灵感不会被强行加入商业分析；
9. 验证候选不足时不会用低相关项目凑数。

## 12. 第一阶段边界

第一阶段只建立稳定、可重复使用的 Codex 工作流和 Markdown 灵感库，不包含：

- 独立 Web 或桌面应用；
- 多用户、账号和权限；
- 支付、订阅或商业化系统；
- 数据库和独立后端；
- 自动定时刷新所有旧报告；
- 未经用户决定就开始开发某个灵感。

当积累约 10–20 个真实灵感后，再根据真实使用频率决定是否增加图形界面、数据库、自动趋势追踪或产品化能力。
